# Sudoers provisioning — letting enrolled standard users run curated `sudo`

macOS `sudo` gates on `/etc/sudoers` (and `@includedir /etc/sudoers.d`): a
user who is not named there for a given command is refused. So a plain
standard (non-admin) user cannot run any `sudo` command, no matter what
Serberus rules say — Apple's sudo refuses them at the coarse layer. sudo does
authenticate them first, so `pam_serberus` still sees the request (see
[below](#why-a-bare-standard-user-is-intentionally-denied-until-enrolled)),
but no Serberus answer can make sudo run it.

This feature closes that gap **per-command and fail-safe**. When an admin enrolls
standard users (the `sudoEnrollment` config key), the Serberus daemon generates a
managed drop-in at **`/etc/sudoers.d/serberus`** that lists *only the curated
allow/prompt command paths* for the enrolled principals. That coarse grant lets
`sudo` invoke PAM; `pam_serberus` + the daemon then apply the **authoritative fine
policy** (argv matching, prompt/approve, deny, TeamID/hash pins, grant caching).

> **One-sentence security model.** The sudoers drop-in is a *coarse outer
> allowlist* that bounds an enrolled standard user's blast radius to the curated
> command paths; `pam_serberus` + the daemon remain the *authoritative fine
> policy*. Neither replaces the other, and the drop-in is deliberately weaker than
> the fine policy so it can never widen it.

---

## Two-tier model

| Tier | Mechanism | Decides | Authoritative for |
|---|---|---|---|
| **Coarse (this doc)** | `/etc/sudoers.d/serberus`, generated by the daemon | *May this principal invoke `sudo` for this command **path** at all?* | Reaching the PAM stack. Nothing finer. |
| **Fine** | `pam_serberus.so` → daemon rule engine | ALLOW / PROMPT / DENY on the full request (argv, elevation, identity pins, grants) | The actual authorization decision |

Because `pam_serberus` **passes the auth through** to the daemon's fine policy
(see [`SerberusPAM.md`](SerberusPAM.md)), the sudoers file is the **only** thing
bounding an enrolled standard user to curated paths. That is why it must stay
strictly narrower than the fine policy — hence the invariants below.

### Why a bare standard user is intentionally denied until enrolled

This is by design, not a bug:

sudo authenticates the user before it applies sudoers' verdict, so the PAM
stack, and with it `pam_serberus`, runs even for a request sudoers will
refuse. The daemon evaluates and logs it like any other.

- **Not enrolled** (not in the drop-in, not an admin) → `pam_serberus` asks the
  daemon, then Apple's sudo refuses at the sudoers layer (`user is not in the
  sudoers file`). **Fail-safe: denied**, whatever Serberus answered.
- **Enrolled**, command path **in** the drop-in (an allow/prompt rule) →
  `pam_serberus` runs → daemon fine policy decides ALLOW / PROMPT → sudoers
  permits.
- **Enrolled**, command path **not** in the drop-in (a deny rule, a `.regex`/`.any`
  rule, or simply no allow rule) → `pam_serberus` runs → the daemon denies,
  or, if some rule allows it, sudoers refuses afterwards. Net **DENY**.
- **Admin** (already covered by the stock `%admin ALL=(ALL) ALL`) → `pam_serberus`
  runs (if wired) → daemon fine policy decides, including deny rules like
  `deny-shutdown` → sudoers permits everything.

The practical consequences for runbooks: a request sudoers refuses still
shows up in the decision log. A deny rule's message, not sudo's "not in the
sudoers file", is what the user sees when the daemon denies. And a prompt
rule can raise the Sentinel dialog, and an approval record a grant, for a
command sudoers then refuses. This was confirmed on a real Mac (macOS 26.7,
sudo 1.9.17p2, 2026-09-28). For a user who isn't enrolled, a deny is
followed by sudo's `Sorry, try again.` and, after three tries,
`3 incorrect password attempts`, because the drop-in's settings that end
sudo's retries apply only to enrolled users; the decision log has one
`denied` line.

## What the drop-in contains

The daemon translates the current rules into sudoers with a pure generator
(`SudoersGenerator` in `PrivMgrCore`). It reads **only** rules where
`type == .sudo && action == .allow` — the union of silent-allow and
prompt-elevation rules (a "prompt" rule is `action == .allow` with
`elevation.type == .prompt`, so both qualify). `action == .deny` rules are **never
a source**. Per-argument (`argPattern`), `requiredTeamID`, and `requiredBinaryHash`
are **ignored** for the coarse layer — those identity/argv pins are things sudoers
cannot express, and the daemon enforces them.

### Match-type translation

| Rule `matchType` | Emitted? | Sudoers spec produced |
|---|---|---|
| `.exact` (default when nil) | ✅ | the path as written **and** its symlink-resolved form when they differ (one or two specs; `.allowMissing` so an absent binary doesn't drop the rule). A path containing a glob metacharacter `* ? [ ]` is **excluded**, because sudoers would treat it as a live wildcard and visudo rejects the escaped forms |
| `.glob` | ✅ | one wildcard spec, **not** canonicalized; sudoers `fnmatch(3)` metacharacters `* ? [ ]` stay live wildcards, other unsafe chars escaped |
| `.prefixRegex` | ✅ | `<prefix>` and `<prefix>/*` (component-boundary semantics) for the prefix as written **and** for its symlink-resolved form when they differ: up to **four** specs. A prefix that contains glob metacharacters is not resolved and keeps them as live wildcards |
| `.regex` | ❌ excluded + logged | not representable in sudoers |
| `.any` | ❌ excluded + logged | would be an ALL-commands grant — **forbidden** |
| nil `commandPattern` (e.g. an authURI rule) | ❌ excluded | no path to emit |

An excluded rule is **fail-safe**: excluding a command leaves it denied at the
sudoers gate, and every exclusion is recorded for loud logging. A path that
resolves to contain a newline / CR / NUL / control character is likewise excluded
(not aborting the whole body), and so is a path containing a backslash (sudoers
has no form for one) or one that isn't absolute. Accepted paths have the
sudoers metacharacters `#`, space, comma, colon and equals backslash-escaped,
so one path can never split into two command specs. `!` is left as it is:
mid-path it is literal, and visudo rejects `\!`.

### Body shape

```
# /etc/sudoers.d/serberus: managed by com.herojoneslabs.serberus — do not edit
Defaults:jane timestamp_timeout=0
Defaults:jane !env_keep
Defaults:jane passwd_tries=1
Defaults:jane authfail_message="denied by Serberus - see the message above"
Defaults:jane badpass_message="denied by Serberus"
Defaults:%serberus-sudoers timestamp_timeout=0
Defaults:%serberus-sudoers !env_keep
Defaults:%serberus-sudoers passwd_tries=1
Defaults:%serberus-sudoers authfail_message="denied by Serberus - see the message above"
Defaults:%serberus-sudoers badpass_message="denied by Serberus"
jane ALL = /bin/echo, /usr/bin/true
%serberus-sudoers ALL = /bin/echo, /usr/bin/true
```

- First line is the managed header (`BundleConfig.sudoersManagedHeader`), also the
  marker the teardown helper greps for.
- Five `Defaults:` lines per principal. `timestamp_timeout=0` turns off sudo's
  per-tty credential cache, so every curated command goes back through
  `pam_serberus`. `!env_keep` empties the kept-variable list, so a curated
  command runs with root's `HOME` and sudo's standard `PATH`, never the user's
  (macOS's `/etc/sudoers` keeps `HOME`, `MAIL`, `EDITOR` and `VISUAL`, and sudo
  keeps `PATH` by default; each would point root at files the user controls).
  `passwd_tries=1` and the two message settings make a Serberus deny read as
  one line instead of a failed-password loop.
- One command line per principal: a user is its literal name; a group is `%<group>`.
- Command specs are collected into a set (dedup) and sorted deterministically;
  enrollment users are sorted and the group line is appended **last** →
  **byte-identical output for identical inputs**, so the daemon's change-detection
  doesn't churn the file.

### Invariants — what is **never** emitted

Because the drop-in is the sole coarse bound on an enrolled standard user, the
generator (and the visudo backstop) guarantee it never widens beyond the curated
allow/prompt paths:

- **Never `NOPASSWD`.** Omitting it means every `sudo` still traverses the PAM
  stack → `pam_serberus` → the daemon. A `NOPASSWD` tag would skip PAM entirely and
  hand the enrolled user the command with *no* fine policy at all.
- **Never an `ALL` commands token.** `.any` and nil-pattern rules are excluded, not
  translated. The drop-in only ever names explicit curated paths.
- **Never a `deny` line / deny-inversion.** Deny is the daemon's job. The coarse
  layer only ever *adds* narrowly-scoped permission; it never encodes a denial.
- **Run-as is root only.** The runas spec is omitted (`= <cmd>`), which means
  run-as-root — correct for curated admin `sudo`.

### Empty enrollment → the file is removed

`SudoersGenerator` returns an **empty body** (signalling *remove the file*, never
*install a header-only file*) when either:

1. enrollment is empty — `group` nil-or-blank **and** `users` empty; or
2. every candidate command was excluded (a principal line with zero commands is
   invalid sudoers).

Removing an enrolled user or clearing `sudoEnrollment` therefore deletes
`/etc/sudoers.d/serberus`, dropping those standard users back to fail-safe
"denied" — no lingering grant.

## Named enrollment — the `sudoEnrollment` config key

`sudoEnrollment` lives in the **CONFIG** domain
(`com.herojoneslabs.serberus.config`), not the frozen rules wire schema. It is a
native-plist dict-of-arrays, parallel to `pamBypass`:

```xml
<key>sudoEnrollment</key>
<dict>
    <key>group</key>
    <string>serberus-sudoers</string>
    <key>users</key>
    <array>
        <string>jane</string>
        <string>sam</string>
    </array>
</dict>
```

- `group` *(string, optional)* — a **pre-existing** local/directory group; all its
  members become enrolled. Omit the key entirely for no group (do **not** set it to
  an empty string as a placeholder).
- `users` *(array of strings)* — individual enrolled usernames.
- **Absent / empty** `sudoEnrollment` = empty enrollment = **drop-in removed**
  (fail-safe default). A bare install with no config enrolls no one.

Deliver it as a **native plist dict** in an MDM configuration profile
(`Application & Custom Settings` on `com.herojoneslabs.serberus.config`).
Serberus reads only the managed layer, so a value set with `defaults write` or
`defaults import` is ignored. A JSON *string* in its place is the wrong type:
it enrolls no one, and the daemon reports `degraded (config_invalid)`.

> Group/user names with **internal whitespace** match no real principal; the
> authoring UI rejects them before publish. Names are not otherwise validated
> against the directory — see the group-must-pre-exist limitation below.

## IdP-group enrollment (console user only)

Named enrollment, above, enrolls the `users` and `group` you list. IdP-group enrollment lets an admin enroll the
**current console user** dynamically when that user's IdP (e.g. Entra) group
membership matches a configured list — *without* naming them ahead of time. It is
**opt-in and off by default** (`idpSource == .disabled`): with the key unset the
resolver never runs and IdP-group enrollment contributes nothing.

Jamf Connect writes its state file owned by the user. With the default
`requireRootOwnedState = true`, Serberus refuses that file, so turning IdP-group
enrollment on also means either providing a root-owned state file or opting into user-owned state file mode
with `requireRootOwnedState = false` and accepting its
[residual risk](#residual-risk-of-user-owned-state-file-mode).

The resolver (`IDPGroupResolver` in `PrivMgrCore`) produces **only** the
daemon-verified console-user name, which is then handed to the **unchanged**
hardened `SudoersGenerator` as an extra individual `users` entry. Everything the
main body says about the drop-in still holds: the emitted grant is the curated
allow/prompt paths only, never `NOPASSWD`, never `ALL`, never a deny line, run-as
root only, and every principal is re-validated by `SudoersGenerator`'s
`isSafePrincipalName`.

### Config keys (CONFIG domain, inside `sudoEnrollment`)

All keys live in the `sudoEnrollment` dict on `com.herojoneslabs.serberus.config`,
alongside `group`/`users`:

| Key | Type | Default | Meaning |
|---|---|---|---|
| `idpSource` | string | `disabled` | Source of the membership hint. `disabled` = IdP-group enrollment off (resolver never runs). `jamf_connect_state` = read the Jamf Connect state cache. Fail-closed parse: any unknown value falls back to `disabled`. |
| `idpGroups` | array of strings | `[]` | Entra group names or GUIDs to match. Empty ⇒ **no one is ever enrolled from a hint**, regardless of `idpSource`. GUIDs match with or without `{ }` braces; matching is case-folded. |
| `idpStatePath` | string | `Library/Preferences/com.jamf.connect.state.plist` | **Home-relative** subpath to the state file, joined onto the console user's `getpwuid` home directory. A leading `/` or any `..` component is rejected (no enrollment). |
| `idpGroupsKey` | string | `UserGroups` | The array key inside the state plist holding the group hints. |
| `requireRootOwnedState` | bool | `true` | `true` (strict, the default): require the file to be **root-owned and not owner-writable**, with exactly one hard link (`st_nlink == 1`) and on the same device as the user's home folder, so a user can't forge their own membership (needs an MDM- or Jamf Connect-dropped root-owned file). `false` (advisory, opt-in): accept the user-owned, user-writable state file and log a warning; see the residual risk below. |

Example config-profile payload (native plist dict, delivered via MDM
`Application & Custom Settings` on `com.herojoneslabs.serberus.config`):

```xml
<key>sudoEnrollment</key>
<dict>
    <!-- IdP-group enrollment: dynamically enroll the console user by Entra-group hint -->
    <key>idpSource</key>
    <string>jamf_connect_state</string>
    <key>idpGroups</key>
    <array>
        <string>Test-Name</string>
        <string>{xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx}</string>
    </array>
    <key>idpStatePath</key>
    <string>Library/Preferences/com.jamf.connect.state.plist</string>
    <key>idpGroupsKey</key>
    <string>UserGroups</string>
    <key>requireRootOwnedState</key>
    <true/>
</dict>
```

`group` and `users` remain orthogonal — you can combine named enrollment
with IdP-group enrollment in the same dict, or omit them for IdP-group enrollment only.

### Trust model

- **Console-user-only resolution.** The resolver's *only* possible output is the
  daemon-supplied, verified `ConsoleUser.name`. The console user is resolved by
  `ConsoleUserResolver` from `SCDynamicStoreCopyConsoleUser` + `getpwuid`: the
  name and home directory come exclusively from the passwd record, the passwd
  short name must agree with the `SCDynamicStore` console name, and root /
  `loginwindow` / sub-501 uids are refused. The group hint selects **whether**
  that one verified name is enrolled — it can never substitute a *different*
  name. A fully attacker-controlled claim can at most add the attacker's **own**
  current console username to the already-curated set.
- **TOCTOU-safe read.** `JamfConnectStateSource` opens the state file
  `O_RDONLY | O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK` (no symlinked final component,
  no fifo stall), makes every ownership / mode / regular-file decision against
  the `fstat` of the **open descriptor** (no check-then-swap window). In every
  mode that `fstat` must also show one hard link and the home folder's device,
  so a hard link to some other root-owned file, or a file on a volume mounted
  inside the home folder, is refused. It then reads the
  bytes directly, and parses with `PropertyListSerialization` — **never**
  `CFPreferences` (which would consult the managed layer / caches instead of this
  exact file). A size cap (1 MiB) guards the read.
- **Strict mode trusts any root-owned copy of the file.** The state file lives
  in the user's own `~/Library/Preferences`, a folder the user controls. A user
  who kept an earlier root-owned state file (from a time they were in a
  configured group) can move it back into place, and strict mode accepts it.
  Closing this needs the state file in a location only root can write.
- **Opt-in / default-off, fail-safe everywhere.** `idpSource` defaults to
  `disabled` and the parse is fail-closed. Every off-path — disabled, empty
  `idpGroups`, no verified console user, missing/stale source, any ownership or
  symlink refusal, a strict-mode rejection, or simply no matching group — yields
  **zero** enrolled users. Enrollment happens on exactly one path: a non-empty
  intersection of `idpGroups` with the claim after normalization.

### Audit events to monitor

The daemon logs at most one `idp-resolve.*` outcome line per provisioning pass
(mapped from `IDPResolveEvent` in `DaemonController.emitIDPResolveEvent`), plus
one `idp-resolve.revoked` line for each user who dropped out. The daemon's
integrity `os.Logger` stream also carries the lower-level `idp-source:` and
`console-user:` warnings. These are the lines it logs:

| Event | Meaning | Operator action |
|---|---|---|
| `idp-resolve.granted` | The one enrollment path — a configured group matched; the console user's name was added to the drop-in for the matched groups. | Expected in normal use; alert on unexpected users/groups. |
| `idp-resolve.no-match` | A valid claim was read but no configured group matched → not enrolled. | Benign; useful for confirming scoping. |
| `idp-resolve.refused.ownership` | The state file failed the owner/mode check (not owned by the console user in user-owned state file mode, group/other-writable, or owner-writable in strict mode). Logs `uid` + octal `mode`. | Investigate — misconfiguration or tampering. |
| `idp-resolve.refused.symlink` | The path resolved through a symlink or a non-regular file. | Investigate — likely a tamper attempt. |
| `idp-resolve.refused.strict` | `requireRootOwnedState` is on and the state file is not root-owned, or it fails the hard-link check (more than one link, or not on the home folder's volume), even when root-owned. | Expected if Jamf Connect's user-owned file is in place and no root-owned file was provided. |
| `idp-resolve.refused.timeout` | Reading the state file took longer than the daemon's time limit → nobody enrolled. | Investigate — a hung volume or a blocking file at the state path. |
| `idp-resolve.stale` | The state file is missing or unreadable, or has no groups key → nobody enrolled. | Check that Jamf Connect has written its state file, and `idpStatePath` / `idpGroupsKey`. |
| `idp-resolve.revoked` | A previously-enrolled console user no longer matches (logout, claim changed, or a strict/ownership refusal now firing) → the drop-in is rebuilt without them and any session grant is revoked. | Confirms de-provisioning on session/hint change. |

Three outcomes are deliberately silent, because they are expected and would
flood the log: IdP-group enrollment disabled, empty `idpGroups`, and no verified console user
(nobody at the console, `loginwindow`, a root/system uid, or a name mismatch). All
of them mean **no one was enrolled**. A root-owned but owner-writable file in
strict mode is logged as `refused.ownership`, not `refused.strict`.

### Residual risk of user-owned state file mode

> **Residual risk.** A user who can tamper their own Jamf Connect state plist can
> grant themselves the CURATED sudo commands for their own session (bounded to the
> curated allow-list, still pam_serberus-gated, never root/ALL/NOPASSWD/deny-bypass);
> this is NOT an attestation of real Entra membership.

This is the trust boundary you accept by opting into user-owned state file mode
(`requireRootOwnedState = false`): the state file is user-owned and
user-writable, so its group array is a *self-asserted hint*, not proof of
directory membership. The containment is that the blast radius of a forged hint
is exactly the same curated, per-command, `pam_serberus`-gated allow-list the
admin already published — for the forger's own account only. The default,
`requireRootOwnedState = true`, requires a root-owned state file the user cannot
write, and refuses the user-writable one.

### Platform SSO customers use named enrollment, not IdP-group enrollment

IdP-group enrollment is **infeasible under Platform SSO (PSSO)**: a root daemon cannot read a
PSSO user's raw Entra group claims — there is no user-readable or daemon-readable
state file equivalent to the Jamf Connect cache to consult. PSSO deployments must
therefore use **named enrollment**: map the Entra group to a **local** group out of band
(via PSSO/MDM group mapping) and set `sudoEnrollment.group` to that local group
name (the generator renders it as the `%<group>` stanza). Named enrollment carries no
residual risk of IdP-group enrollment because local-group membership is directory-enforced, not
self-asserted.

## Safety flow (daemon install)

A malformed sudoers file breaks `sudo` for **everyone**, so the daemon's
`SudoersManager` applies a strict, fail-closed pipeline:

1. **Generate** the body (pure `SudoersGenerator`).
2. **Pre-screen** — reject any newline/control character.
3. **Write a temp file OUTSIDE `/etc/sudoers.d`** (on the same volume as `/etc`, so
   the install can be an atomic rename). A half-written file *inside* the
   `@includedir` would be parsed by the next `sudo`.
4. **`visudo -c -f <tmp>`** — validate. The runner is **timeout-bearing**; a hung
   `visudo` is treated as a validation failure (fail closed).
5. **Only on exit 0**, atomically rename into `/etc/sudoers.d/serberus` as
   **`root:wheel`, mode `0440`**.
6. **On any failure/timeout**, do **not** install: keep the prior good file (or
   remove if none) and log loudly with the captured `visudo` stderr.
7. **Empty body** (empty enrollment or all-rules-excluded) → **remove** the
   marker-guarded drop-in rather than write anything.

The drop-in is **enforce-only**. The daemon writes it only when
`enforcementMode` is `enforce`. In `monitor` and `audit` (including the
awaiting-config bootstrap) `pam_serberus` passes sudo straight through, so a
drop-in there would give an enrolled standard user ungated sudo on the curated
paths. The daemon therefore actively removes it in those modes, and under the
kill switch (`daemonEnabled == false`). When the mode leaves `enforce`, removing
the drop-in is the first thing the daemon does, and it reloads as soon as the
config profile changes rather than on its next 30-second tick.

`pam_serberus` covers the moment in between: while the drop-in is still on
disk, it evaluates every non-bypass user as in `enforce` mode, even in
`monitor`, `audit`, bootstrap or under the kill switch. See
[SerberusPAM.md](SerberusPAM.md#authentication-flow).

The daemon also writes the drop-in only when the fine gate is really wired:

- the first active `auth` line of Apple's `/etc/pam.d/sudo` is
  `auth include sudo_local`;
- `/etc/pam.d/sudo_local` has an active
  `requisite /usr/local/lib/pam/pam_serberus.so` line above every other active
  `auth` line;
- neither file has any other `include` line, and every other module either
  file names is on a root-only path (see
  [SECURITY.md](../SECURITY.md#what-serberus-is-designed-to-enforce)); and
- both files, the module and its parent directories are root-owned and not
  group- or other-writable.

If any check fails, the daemon removes the drop-in and reports `degraded`
with reason `pam_not_wired`.

Sudoers provisioning is otherwise **non-fatal to the daemon** — a write failure
does not degrade daemon state; it just leaves the last good drop-in (or none) in
place. The daemon re-applies on every policy/config reload, and gates reconcile
on a signature that includes `sudoEnrollment.group`/`users`, so an
enrollment-only change still triggers a rebuild.

To verify a live install:

```bash
sudo ls -le /etc/sudoers.d/serberus        # -r--r-----  root  wheel
sudo head -1 /etc/sudoers.d/serberus       # the managed header
sudo visudo -c                             # whole sudoers set parses cleanly
```

## Teardown ordering — coarse grant removed **before** the fine gate

**Order is the safety property.** The drop-in is the coarse grant; `pam_serberus` +
the daemon are the fine gate. If teardown removed the fine gate (unwired
`sudo_local` / removed the module / stopped the daemon) while the coarse grant
still existed, an enrolled standard user would run the curated commands through
Apple's plain `sudo` stack with **no argv/deny/prompt policy** — a
privilege-escalation bypass. So every teardown path removes
`/etc/sudoers.d/serberus` **first**:

1. Remove `/etc/sudoers.d/serberus` (marker-guarded — the helper greps for the
   managed header so a same-named admin file is never destroyed; touches only that
   one path; no `visudo` needed, since removing one independently-parsed
   `@includedir` file cannot invalidate the rest).
2. *Then* unwire `sudo_local`, stop the daemon, demote JIT admins, restore the
   authdb, and remove the PAM module and the other files.

Removing coarse-first only ever fails standard users **closed** at the sudoers gate
(safe). Removing it after the fine gate is unwired opens the bypass window. Removal
is unconditional (it is active security config, not gated behind a `--purge` flag).

The daemon also offers `serberusd --remove-sudoers` for symmetry with
`--restore-authdb`, but the pkg teardown scripts use an inline marker-guarded `rm`
so they stay independent of the daemon binary.

## Known limitations & follow-ups

1. **The enrollment group must pre-exist.** `sudoEnrollment.group` is assumed to
   already exist as a local/directory group; **local-group creation is out of
   scope** for this feature. If the named group does not exist, its (nonexistent)
   members simply aren't enrolled — the `%<group>` line still renders, but no real
   user matches it. Create the group (e.g. via MDM/`dseditgroup`) out of band, or
   enroll individual `users` instead. Operators must **not** assume Serberus
   auto-creates the group.
2. **The `visudo` timeout** added for this feature (in the daemon's process runner)
   is a general fail-closed improvement other Serberus shell-outs could adopt.
